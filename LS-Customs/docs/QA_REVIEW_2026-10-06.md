# LS Customs QA review — 6 October 2026

## Release assessment

**Do not approve for production release until the critical access-control and emergency-dispatch issues are resolved.** This assessment combines live guest testing with source review; it is not a certification of the deployed database or a completed authenticated penetration test.

Evidence labels:
- **Live:** observed on https://ls-customs-web.vercel.app/.
- **Check:** reproduced by running a repository command.
- **Source:** concrete defect in the checked-out implementation. Deployment exploitability requires confirming the deployed schema/functions match this checkout.
- **Conditional:** impact depends on deployment configuration or business policy.

No production bookings, payments, messages, account changes, or exploitation were performed. Docker Desktop's Linux engine was unavailable, so database/RLS integration tests could not run locally. No customer or admin test session was available. The deployed frontend may differ from the checkout. Contrast, screen-reader announcements, Android behavior, and authenticated flows need further testing.

## Security and integrity findings

### QA-01 — Critical: customer profile updates allow role escalation [Source]
Evidence: `apps/backend/supabase/migrations/20260819120524_rls_policies.sql:78` permits updating an owned profile with only an ID ownership check. `20260819120535_grants.sql:19` grants table-wide UPDATE. The policy comment promises a role-protection trigger, but the migration set contains no implementation restricting changes to `profiles.role`.

Impact: a customer can request a role change through the Data API; `is_admin()` and admin Edge Functions subsequently trust that same role. This can expose other customers' data and privileged operations.

Fix: enforce immutable privileged fields for customers at the database boundary and use a separately authorized admin role-management operation. Regression test: customer role updates fail and permitted name/phone updates succeed.

### QA-02 — High: the browser controls payable prices and booking fields [Source]
Evidence: MechanicBookingFlow.tsx:209 and Rentals.tsx insert calculated `total_price`; service items also accept browser `price_at_booking`. The insert RLS rules check ownership/status, not catalog prices. create-payment-intent/index.ts:221 charges the stored total without recalculating it.

Impact: a caller can submit a reduced price directly and have the payment API use it. Vehicle INSERT also does not force pending status. The live-location UPDATE policy in `20260901120000_service_bookings_live_location.sql:34` allows entire-row updates, despite its comment claiming to permit only location columns; customers can change other fields while maintaining its required status/coordinates.

Fix: create bookings through a transactional server operation that calculates prices, verifies promotions, restricts editable fields, validates ownership of related addresses, and sets workflow state. Test altered totals, status, mechanic IDs, address IDs, and non-location changes.

### QA-03 — High: notification authentication trusts a client-supplied object [Source]
Evidence: dispatch-notification/index.ts:325 authenticates any request containing `record.id`, without a signature or verified internal credential.

Impact: a customer able to reach the function can forge webhook-shaped JSON and access its privileged notification delivery path. Gateway JWT enforcement can require a valid token, but does not prove the JSON came from an internal webhook. Provider setup determines whether actual SMS/email is sent.

Fix: authenticate internal delivery with a verified credential/signature; remove the body-shape bypass and validate permitted recipients/actions. Test a normal customer JWT with forged `record` data and expect rejection.

### QA-04 — High: known admin passwords are provisioned by migrations [Source, conditional]
Evidence: `20260909160000_seed_admin_account.sql` and `20260924120000_seed_additional_admins.sql` contain fixed admin accounts/passwords; some upsert paths reset password hashes. Credentials are intentionally omitted from this report.

Impact: applying these migrations to a hosted database can create predictable privileged logins. Live account presence was not tested.

Fix: remove privileged demo provisioning from deployable migrations, rotate affected deployed credentials, and provision real administrators through an invitation process. Verify no known seeded password authenticates in staging/production.

### QA-05 — High: mechanic GPS coordinates are public [Source]
Evidence: `20260921130000_get_dispatch_mechanics.sql:37` grants anon/public access to a SECURITY DEFINER RPC returning named mechanics and current coordinates. The assigned-customer SELECT policy also lacks a terminal-status restriction.

Impact: anonymous callers can obtain available mechanics' precise locations; former customers may retain location visibility through completed bookings.

Fix: expose approximate discovery/distance results and permit precise tracking only for an active authorized assignment, subject to mechanic consent. Test anonymous and completed-booking access.

### QA-06 — High: receipt delivery can bypass booking validation and falsify payment status [Source]
Evidence: send-receipt/index.ts accepts caller-supplied recipient/content/amount. Ownership checks run only when a lookup returns a row. A nonexistent booking/payment ID can proceed when an email was supplied, and the generated status is always `Confirmed & Succeeded`. `_shared/resend.ts` inserts supplied strings into HTML without escaping.

Impact: an authenticated caller can request misleading receipts to arbitrary recipients, including receipts for unpaid/nonexistent bookings and injected email markup. This is an email-content injection finding, not a demonstrated browser script-execution exploit.

Fix: require an existing owned paid transaction, derive content and recipient from stored records, escape HTML, and rate-limit/deduplicate delivery. Test nonexistent IDs, unpaid bookings, altered recipients, and markup strings.

## Booking, payment, and dispatch defects

### QA-07 — High: customer cancellation uses a nonexistent column [Source]
Evidence: Bookings.tsx:242 filters both booking tables on `user_id`; the schema uses `customer_id`.

Impact: cancellation fails instead of cancelling an owned pending booking. Fix the filter and assert the affected row count. Test both rental and mechanic cancellations with an actual customer session.

### QA-08 — Critical: emergency dispatch announces success without real acceptance [Source]
Evidence: EmergencyMechanicModal.tsx:248–318 runs timed success messages and creates an active dispatch with a fixed mechanic and nine-minute ETA even for guests or failed booking inserts. Assignment responses are not validated.

Impact: stranded customers can be told help is coming when nobody accepted their request.

Fix: show success only after a persisted request and real dispatch acceptance; display failure/no-capacity states and a real support fallback. Remove synthetic acceptance from customer production flows. Test guest requests, insert failure, assignment 409, network loss, and real acceptance.

### QA-09 — High: emergency cancellation affects only local UI [Source]
Evidence: EmergencyMechanicModal.tsx:321 clears `activeDispatch` without cancelling the saved booking or informing dispatch.

Impact: the customer sees cancellation while a backend booking can remain active. Fix through an authorized server cancellation and update the UI only after acknowledgement. Test state after reload and from the dispatcher's view.

### QA-10 — High: tracker telemetry is simulated [Source]
Evidence: VirtualMechanicTracker.tsx:40 uses timers, random speed changes, and a drawn curve. Emergency UI labels the experience as live GPS tracking.

Impact: speed, distance, route, and ETA may mislead customers. Replace with actual authorized mechanic telemetry, show its timestamp/accuracy, and mark stale data explicitly. Test stopped telemetry and offline mechanics.

### QA-11 — High: reusing a pending payment returns an invalid checkout contract [Source]
Evidence: create-payment-intent/index.ts:210–215 returns `provider_reference` as both client secret and checkout URL and omits amount/currency. `_shared/paymentProvider.ts` stores provider IDs separately from client secrets/URLs. PaymentForm calls amount formatting methods.

Impact: reopening payment can crash rendering or use the wrong payment URL/secret. Fix by retrieving/persisting the actual provider session fields and returning the complete original response shape. Test retries for both providers.

### QA-12 — High: customers cannot resume abandoned unpaid bookings [Source]
Evidence: Bookings.tsx:278 offers retry only for `failed` payments; pending payments have no resume action, and bookings without payment rows display only a message at line 307.

Impact: closing checkout or navigating away can strand a valid booking. Add Pay now/Resume checkout for eligible unpaid states and expired-session recovery. Test reloads before and after creating a payment intent.

### QA-13 — High: mechanic booking creation is not atomic [Source]
Evidence: MechanicBookingFlow.tsx:209–228 inserts a booking and then a service item in separate calls. Item failure leaves the booking behind. Returning from payment to review allows another confirmation insert.

Impact: incomplete and duplicate bookings. Use one transaction with an idempotent request identifier; edit/reuse the existing draft when navigating back. Test item-insert failure and repeated confirm/back/confirm actions.

### QA-14 — High: webhook processing can lose reconciliation or regress state [Source]
Evidence: payment-webhook/index.ts:143 acknowledges missing rows/database lookup errors; line 162 skips processing when the payment already matches the event state; line 205 confirms rentals without guarding current booking status. Booking-update errors are logged and then acknowledged.

Impact: payment can be marked paid while booking confirmation fails permanently on retries; late events can overwrite newer payment state; a cancelled rental can be reconfirmed. Persist verified events, enforce legal transitions, reconcile payment and booking atomically, and retry transient failures. Test out-of-order/replayed events, cancelled bookings, and injected booking-update failures.

### QA-15 — High: unpaid rental holds have no visible expiry mechanism [Source, conditional]
Evidence: the overlap constraint includes `pending` rentals. No hold-expiry cleanup was found in the provided migrations/functions; an external scheduled job was not inspected.

Impact: abandoned reservations can block fleet availability indefinitely, and automated accounts can exhaust inventory. Add a short server-enforced hold expiry, cleanup, and per-customer reservation limits. Test abandoned checkout and expiry under concurrent requests.

### QA-16 — Medium: rental endpoint date semantics conflict [Source]
Evidence: the exclusion constraint uses `daterange(..., '[]')`, while availability queries compare against requested `[)` ranges and the frontend charges the end-start day difference.

Impact: availability and insertion can disagree at boundaries; same-day return/pickup reuse may be blocked unexpectedly. Define the business interval once and use it in price, availability, and exclusion rules. Test adjacent and overlapping rentals.

### QA-17 — High: mechanic assignment does not reserve schedule capacity [Source]
Evidence: assign-mechanic selects `is_available` mechanics and writes the booking without a schedule-overlap reservation, conditional pending update, or transactional mechanic lock. It does not check payment. StepSchedule.tsx displays fixed slots without capacity lookup.

Impact: concurrent requests can assign overlapping work or overwrite assignments. If payment is intended to unlock ordinary dispatch, customers can invoke assignment before paying. Build transactional capacity reservations with service duration/travel buffers; make payment policy explicit (including emergency exceptions). Test concurrent assignments and occupied slots.

### QA-18 — High: failed emergency geolocation falls back to a dispatchable default pin [Source]
Evidence: EmergencyMechanicModal.tsx initializes fixed coordinates and changes only the text on location failure. Dispatch can still use those coordinates.

Impact: help may be requested for the wrong location. Require customer-confirmed address/pin when GPS fails, verify coverage, and show the location being sent. Test denied GPS, timeout, inaccurate fix, and out-of-coverage locations.

### QA-19 — Medium: guest mechanic availability bypasses the intended public read path [Source, live symptom]
Evidence: MechanicServices.tsx queries `mechanic_profiles` directly, but the base-table SELECT policies restrict this to self/admin/assigned customers. A public discovery RPC exists. Live guest UI displayed no mechanics available, but actual fleet capacity was not independently checked.

Impact: guests can see a false no-capacity message. Use the public discovery RPC, distinguish permission/network errors from an empty fleet, and provide retry.

### QA-20 — Medium: catalog failures appear as empty inventory [Source]
Evidence: useServices exposes error/refetch, but MechanicServices and MechanicBookingFlow discard those error fields.

Impact: customers cannot distinguish a loading outage from an unavailable service. Show an actionable error and Retry, preserving form state. Test API failure and recovery.

## Customer accessibility and sign-in gaps

### QA-21 — High: sign-in modal lacks focus management [Live, source]
Evidence: opening sign-in left focus on the background Sign in button; Escape left the dialog open. The dialog had neither `aria-modal` nor an accessible title association. AuthModal.tsx:134 has no focus-trap/initial-focus implementation.

Fix: move focus inside, keep background inert, contain Tab/Shift+Tab, close on Escape, restore focus, and connect the title. Verify with keyboard and screen reader. Reference: [W3C modal dialog pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/).

### QA-22 — Medium: sign-in and rental search inputs rely on placeholders [Live, source]
Evidence: the live accessibility tree exposed unnamed text fields. AuthModal.tsx:165/190 and rental search provide placeholders without an associated label.

Fix: supply persistent visible labels and associated accessible names; connect hints/errors. Reference: [W3C labels and instructions](https://www.w3.org/WAI/WCAG22/Understanding/labels-or-instructions.html). Formal WCAG conformance needs broader assessment.

### QA-23 — Medium: footer navigation is mouse-only [Live semantics, source]
Evidence: WorkspaceFooter.tsx implements navigation/service actions as click handlers on spans/divs, with no button/link semantics or keyboard handler. The live tree lists these as text.

Fix: use anchors for navigation and buttons for actions. Test all footer destinations with keyboard alone.

### QA-24 — Medium: vehicle cards contain nested interactive controls [Live semantics, source]
Evidence: VehicleCard.tsx gives its article `role=button` and an Enter/Space handler while nesting favorite and booking buttons. The outer key handler can handle bubbled keys from children.

Fix: provide a dedicated details link/control and separate favorite/book actions; verify each keyboard action triggers only its intended operation.

### QA-25 — Medium: OTP recovery and mobile entry features are missing [Source]
Evidence: AuthModal provides no dedicated resend/countdown, phone normalization, OTP input mode/autocomplete, or paste format handling. Terms/Privacy are plain text in the sign-in agreement notice.

Fix: normalize accepted local phone formats, provide resend with throttling/countdown, `autocomplete=one-time-code`, a numeric keypad, clear errors and contact editing, and clickable legal pages. Test delayed/expired OTP, SMS failure, paste, and both email/phone flows. Actual email template compatibility was not verified.

## QA and operational gaps

### QA-26 — High: the test command does not run the existing suites [Check]
Neither backend nor web declares a test script; Turbo only executes a build dependency. Backend `typecheck` runs a secret scanner rather than checking Edge Function types. The integration test file also hardcodes port 54321 while local config uses 15431.

Fix: wire SQL/RLS and Edge Function suites plus meaningful customer-flow tests into CI, parameterize environment/ports, and add a real backend type check. Require actual test counts/results.

### QA-27 — High: TypeScript failure does not block the production build [Check]
The fresh Vite build succeeds while AuthModal's OTP verification call fails TypeScript. This is a compile-time type defect; it does not alone prove OTP fails at runtime.

Fix: construct separately typed email/SMS verify requests and make typecheck a required release gate.

### QA-28 — Medium: lint tooling is not reproducible [Check]
The declared backend lint command falls back to fetching an unpinned ESLint, then fails for missing modern config. Web has no lint script.

Fix: pin tooling, configure it explicitly, and run frontend/backend lint in CI without implicit package installation.

### QA-29 — Medium: configured CORS allowlist does not support every listed origin [Source, conditional]
Evidence: `_shared/cors.ts` exports static headers with the first allowed origin; many functions call jsonResponse without its request argument and OPTIONS also uses the static headers.

Impact: a second authorized origin can fail CORS despite being on the allowlist. Fix per-request origin resolution for both preflight and responses. Test each supported web origin. Wildcard CORS alone is not claimed as an authorization bypass.

### QA-30 — Medium: initial JavaScript is heavy for low-bandwidth customers [Check, performance risk]
Main bundle is approximately 1.78 MB minified / 437 kB gzip. This is a measured bundle size, not a measured page-load regression.

Fix: defer admin screens/payment SDKs and other nonessential routes. Measure startup on throttled mobile connections before setting a performance budget.

## Missing features to prioritize

### Before accepting real customer transactions

1. **Reliable emergency operations:** real acceptance, dispatcher acknowledgement, verified contact numbers, GPS-denied address entry, coverage checks, failure escalation, and real/stale tracking states.
2. **Booking and payment recovery:** resumable unpaid booking, expiring reservation holds, payment reconciliation, and retry that reuses a valid provider session.
3. **Accessible core journeys:** keyboard-operable navigation/modals, labels, clear errors, focus restoration, and screen-reader-tested booking/payment status updates.
4. **Scheduling capacity:** available mechanic slots, service durations, travel buffers, concurrent reservation protection, and a documented dispatch/payment policy.
5. **Transparent transaction terms:** validated pricing/promos and clear deposits, cancellation windows, refund rules, rental inclusions, mileage, fuel, and any delivery fees before payment.

### Next customer-facing additions

6. **Self-service rescheduling, extensions, and refund requests:** show eligibility/fees and request status; preserve booking history. Current refund endpoint is admin-only/full refund.
7. **Downloadable receipt and service history:** genuine paid receipts, payment identifiers, line items, completed work, recommendations, and warranty details. An email endpoint exists but needs the safeguards above.
8. **OTP and account recovery:** resend/countdown, contact correction, alternate verified channel, and clear recovery from provider outages.
9. **Privacy controls:** data export/deletion request workflow, consent for precise tracking, automatic tracking cutoff, and a retention policy. These were not found in reviewed customer views; hosted operational processes may exist separately.
10. **Accessible rental discovery:** filters for wheelchair accommodation, seat/boot capacity, transmission, and special requirements where verified fleet data supports them; publish real photos and verified location/contact details.
11. **Low-bandwidth resilience:** preserve drafts, actionable offline states, lazy loading, and graceful map/provider failure. Avoid claiming a booking/payment succeeded while offline.
12. **Customer trust:** verified reviews/counts, clearly scoped ratings, technician credentials, escalation contacts, and links to actual business social profiles. Sampled fleet cards displayed photo placeholders and generic social homepages.

These are recommendations based on the inspected journeys, not a claim that every item is required by the existing specification. Validate business scope before implementation.

## Suggested repair sequence and acceptance gates

1. Block role escalation, price tampering, forged notification requests, and seeded admin exposure. Prove customer/admin separation with two isolated staging accounts.
2. Replace synthetic emergency success and telemetry; verify dispatch/cancellation against persistent backend state under failure.
3. Repair cancellation, payment reuse/resume, transactional booking creation, webhook reconciliation, and hold expiry.
4. Complete keyboard/screen-reader and mobile core-flow checks; fix sign-in naming/focus and footer/card controls.
5. Enforce TypeScript, reproducible lint, and actual integration tests in CI. Add concurrent booking tests and provider-sandbox checkout/refund/webhook tests.

Remaining validation: deployed RLS/grants, actual admin provisioning, provider credentials/webhook configuration, email/SMS deliveries, Android deep links, payment return after reload, full screen-reader behavior, 200%/400% zoom, contrast, denied geolocation, poor connectivity, rate limits, and load/concurrency. Run these in a disposable staging environment with test-mode providers before signing off.


## Implementation follow-up
