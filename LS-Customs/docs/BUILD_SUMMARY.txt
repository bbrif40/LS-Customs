WHAT WE BUILT
-------------
A Supabase-backed backend for a vehicle rental + mechanic service platform.
It has: 7 PostgreSQL migrations, 6 Edge Functions, and a full test suite.

The project is organized as:

PHASE 1: DATABASE SCHEMA (3 migrations)
---------------------------------------
Goal: Build the data model — what tables exist and what columns they have.

Migrations in order:
  1. 20260819120516_init_enums.sql
     - Defines ENUM types: user_role (customer/mechanic/admin),
       booking_status (pending/assigned/en_route/completed/cancelled),
       service_category.
     - Why enums? They prevent invalid values at the database level.
       If someone tries to insert booking_status = "foo", PostgreSQL rejects it.

  2. 20260819120520_init_schema.sql
     - Creates all tables: profiles, addresses, vehicles, mechanic_profiles,
       mechanic_services, service_bookings, service_booking_items,
       vehicle_bookings, reviews, payments, notifications.
     - The core relationships:
       - A profile (user) owns vehicle_bookings and service_bookings.
       - A mechanic_profile belongs to a profile.
       - A vehicle belongs to vehicles table.
       - Payments link to a booking (vehicle or service).
       - Key constraint: "no_overlapping_bookings" — prevents double-booking
         the same vehicle for overlapping date ranges. Uses PostgreSQL's
         exclusion constraint with daterange.

  3. 20260819120524_rls_policies.sql
     - Row-Level Security (RLS) policies.
     - WHY RLS? Because every request to Supabase comes from a user.
       RLS ensures users can ONLY see their own data. For example:
       - A customer can only see their own bookings (not other customers').
       - Anonymous users can see the vehicle catalog but NOT profiles.
       - The "anon" role is for unauthenticated visitors.
       - The "authenticated" role is for logged-in users.
     - We enable RLS on every table with: ALTER TABLE ... ENABLE ROW LEVEL SECURITY;
     - Then add policies like:
       CREATE POLICY "Users can view own profile" ON profiles
       FOR SELECT USING (auth.uid() = id);
     - Key decision: We verified zero tables have RLS disabled.
       If a table has RLS off, anyone can read ALL its rows. We checked:
       select tablename from pg_tables where schemaname='public' and rowsecurity=false
       → 0 rows = every table has RLS on. Good.

PHASE 2: AUTH TRIGGERS & AUTOMATION (2 migrations)
-------------------------------------------------
Goal: Automate data changes when certain things happen.

Migrations:
  4. 20260819120527_triggers.sql
     - handle_new_user trigger: When someone signs up in GoTrue (auth.users),
       automatically insert a row in public.profiles. This is important because
       profiles stores extra user data (role, full_name) that auth.users doesn't.
       The trigger reads raw_user_meta_data (JSON sent at signup) to get full_name.
     - update_updated_at trigger: Auto-updates the `updated_at` column
       whenever a row changes. Saves you from manually setting it in every UPDATE.
     - enforce_service_status_transition trigger: Prevents invalid status changes.
       For example, a customer can't jump a booking from "pending" to "completed"
       directly. They can only cancel a pending booking. The trigger checks
       the current role and the old/new status, and raises an error if invalid.

  5. 20260819120531_indexes.sql
     - Creates database indexes on foreign key columns and RLS filter columns.
     - WHY index? Without an index, every query does a full table scan.
       With RLS, if your policy filters by user_id, you MUST index user_id
       or queries will be slow. We added indexes on:
       - profiles(id), vehicle_bookings(customer_id), service_bookings(customer_id),
         payments(customer_id), reviews(target_*), etc.

  6. 20260819120535_grants.sql
     - Sets database-level permissions (GRANT/REVOKE).
     - anon role: SELECT on vehicles, mechanic_services, reviews (catalog reads).
     - authenticated role: full CRUD on their own rows (enforced by RLS).
     - service_role: bypasses RLS for internal operations (Edge Functions use this).
       But we still do ownership checks in code — defense in depth.

  7. 20260819120540_phase2_triggers.sql
     - notification_on_status_change trigger: When service_bookings.status changes,
       automatically insert rows into notifications table. The customer gets
       "Booking status changed" and the mechanic gets "New booking assigned".
     - is_admin() function: A SQL function that checks if the current authenticated
       user has role = 'admin' in the profiles table. Used in RLS policies
       to let admins see all data.

DESIGN DECISIONS EXPLAINED
--------------------------

1. WHY use both RLS AND ownership checks in Edge Functions?
   - RLS protects data at the database level (can't be bypassed by bugs).
   - Application-level checks give clearer error messages (403 FORBIDDEN
     vs a generic "no rows returned").
   - This is called "defense in depth" — two layers of security.

2. WHY store role in profiles, not auth.users?
   - auth.users is owned by Supabase's GoTrue service. We can't modify its
     columns or triggers. So we extend user data in public.profiles with
     a foreign key to auth.users(id).

3. WHY use exclusion constraints instead of a CHECK?
   - We need to check if date ranges overlap. A CHECK constraint can't
     reference other rows. PostgreSQL's EXCLUDE USING gist with dage
     range can — it prevents overlapping date ranges for the same vehicle at
     the database level, which is the most reliable enforcement.

4. WHY verify_jwt = false on all Edge Functions?
   - We do manual JWT verification inside each function (extractJwt +
     fetch /auth/v1/user). This gives us more control over error responses
     and lets us pass user context to downstream logic. The KONG proxy
     would auto-return 401 if verify_jwt=true, but we want to handle
     it ourselves so we can return the proper {code, message} envelope.


EDGE FUNCTIONS (5 total)
------------------------
1. assign-mechanic: Finds nearest available mechanic using Haversine distance.
   Takes lat/lng, searches mechanics within radius, assigns nearest one.
   Returns 409 if none available.

2. create-payment-intent: Creates a payment intent with the configured provider
   (PayMongo or Stripe) for a booking.
   Flow: verify JWT → fetch booking → check ownership → call provider API
         → insert payments row (status="pending") → return client_secret.
   Provider is selected via PAYMENT_PROVIDER env var. Both PayMongo and Stripe
   are supported — PayMongo is the default for local dev.

3. payment-webhook: Receives webhook callbacks from the payment provider.
   Flow: verify HMAC-SHA256 signature → parse event type → update payment
         status (pending→succeeded) → update booking status (pending→confirmed).
   CRITICAL: Signature verification happens BEFORE any DB changes.
   Unsigned/invalid webhooks are rejected with 401.
   Supports both PayMongo (Paymongo-Signature header) and Stripe (stripe-signature header).

4. dispatch-notification: Delivers notifications to external channels.
   Sends email via SendGrid and SMS via Twilio. Reads recipient contact info
   from profiles (phone) and auth.users (email via GoTrue admin API).
   Updates notification metadata with dispatch results for idempotency.

5. geocode-address: Server-side wrapper for Google Maps Geocoding API.
   Converts address text to lat/lng coordinates. Verifies JWT, calls Google's
   API, and returns normalized coordinates — avoids exposing the API key
   to the frontend bundle.

6. chatbot: AI customer support assistant for car rental & mobile mechanic services,
   powered by OpenRouter. Routes user messages through an LLM via OpenRouter's
   /chat/completions endpoint (configurable via OPENROUTER_MODEL, defaults to
   the free google/gemma-4-31b-it:free model). Includes topic guardrails that
   intercept out-of-scope requests pre-emptively — no provider call is made
   for blocked messages. Optionally enriches context from user's recent bookings
   when user_id is provided. Public endpoint (verify_jwt=false). Configured via
   OPENROUTER_API_KEY (required), OPENROUTER_MODEL (optional), and
   OPENROUTER_BASE_URL (optional override for self-hosted endpoints).

SHARED CODE:
- _shared/supabaseClient.ts: createServiceClient() (uses service_role key),
  createUserClient(jwt), extractJwt(req) (reads Authorization header).
- _shared/cors.ts: jsonResponse() (consistent JSON envelope), corsHeaders.
- _shared/paymentProvider.ts: Provider abstraction for Stripe/PayMongo.
  Handles payment intent creation, webhook signature verification, and
  event normalization. Both create-payment-intent and payment-webhook
  use this module.

BUGS FOUND DURING VERIFICATION
------------------------------
BUG-01 (Fixed): create-payment-intent returns 500 instead of 401 when
  Authorization header is missing. Root cause: extractJwt() throws a plain
  object {code, message, status: 401} (not an Error instance), but the
  catch block only checks "err instanceof Error" and ignores the thrown
  object's properties. Fix: catch block now checks for plain objects with
  a "status" property and routes to the appropriate error response. Also
  applied the same pattern to dispatch-notification (which had a simpler
  catch that didn't handle non-Error throws). See CLEANUP_REPORT.md.

BUG-02 (Fixed): supabase.functions.setAuth() returns a Promise (async) but
  was not awaited, so the auth header was cleared before the request fired
  and the function returned 401 instead of 403 for authenticated users.
  Fix: added await. See CLEANUP_REPORT.md.
